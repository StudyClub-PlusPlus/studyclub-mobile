# UI State Policy

Main uses loading/content/empty/failure/unavailable; Detail keeps loading/content/empty/failure. Main unavailable means the feature is not provided, rather than an empty response or request failure. Display values are stored before a private CurrentValueSubject sends a read-only publisher notification. Views read the current values; late subscribers receive the current state. Detail requests once from init through a private method and retains its existing missing/invalid/mismatched-ID empty policy.

## Main list requests

Main captures the list flag at creation. The pagination/refresh rules below apply to ON. OFF requests once, disables refresh/loadMore/retryPage, omits the footer and refresh control, and hides collection content behind a state surface. Debug Mock shows its current trusted first-page samples. Real OFF returns featureUnavailable before transport, clears selection and ends loading with unavailable. Real detail OFF returns unavailable before transport and preserves its existing failure state; Mock detail and detail behavior are independent of the list flag.

Main starts the first page from init. It also exposes loadMore, retryPage and refresh for infinite scrolling, failed-page retry and native pull-to-refresh. One stored Task owns the current request. Refresh cancels an older request; a cancelled Task must not mutate display values, requestTask or indicators in success, catch or completion. Repeated refresh and concurrent pagination are suppressed. There is no request generation counter or general request framework.

Initial failure replaces the empty list with failure. Normal zero-result first pages are empty. Loading another page keeps content visible; an error keeps the same cursor and shows a retry footer. A zero-length page while offset<total stops automatic pagination and asks for refresh. Refresh keeps existing content until a successful first page replaces it. Failure preserves content and cursor. Successful empty refresh clears items, lookup dictionary and snapshot. Empty/failure still offer the collection's pull gesture.

Responses use the raw item count to advance the cursor. Main merges IDs while storing each page: duplicates within or across pages keep their first position and receive the last value. Initial load and successful refresh clear the previous list before using the same merge path. No separate duplicate validation is needed; snapshots receive the resulting unique IDs. Content-to-content notifications must reach the controller, so Main does not remove duplicate status notifications. Changed cards with the same ID are explicitly reconfigured in the diffable snapshot. The controller applies snapshots only when IDs, their order or card values change (plus initial section setup). Loading/error indicators update independently. An unchanged successful page still checks whether another page is needed, since its raw cursor may have advanced.

## Account session

Settings reads `auth.google-login` live. In Debug, changing that flag or resetting flags notifies the existing settings screen through the development-settings callback. Other flags do not. OFF hides the account rows, drops login and onboarding, and calls `discardPendingSignup()` without deleting completed credentials. If that cleanup throws, the account rows stay hidden. A root invalidation that fails after that flag is off also stays hidden: it does not show a connection failure or a nickname, and it does not start another restore. A short alert offers another cleanup and does not show a nickname or a login row. Closing it leaves the blocked cleanup and completed credentials in place. It appears only while Settings is visible, and after that close it waits until the user leaves and Settings is visible again. Releasing the settings owner cancels its task without waiting for tab replacement. ON restores through one current task: `checking` shows no nickname, a member result shows only that nickname, confirmed invalid auth is `guest` and does not open login, and `connectionFailure` or `unavailable` keeps credentials and offers recheck. `authenticationInvalid` on restore is `guest`.

Login stays on its existing display states. `configurationMissing` is `unavailable` and does not start a member session. Cancel and close call `discardPendingSignup()` and ignore a later success. The login sheet shows cancelling until that call succeeds. A throw stays on the sheet as cleanup failure, keeps Google disabled, and retries only the cleanup. It does not report cancellation or dismiss. Settings recheck after an on-screen failure repeats the cleanup before another restore. Signup submission is one `completeSignup`. A definite rejection returns to editing with the input kept. An unknown result, including `signupStatusUnknown`, allows `checkSignupCompletion` only. Closing onboarding keeps its input and stays open until discard succeeds, then returns to `guest`. A throw stays on that screen as cleanup failure and retries only the cleanup. It does not submit again, open login, or dismiss. Logout failure keeps the member nickname and can be retried. Flag OFF, logout, cancel and tab replacement invalidate the current task so a late result does not publish. Tab replacement installs the next root only after `invalidate()` succeeds. A throw leaves that root in place and shows a general retry on Main, with no account nickname. Closing that alert leaves the pending replacement and the failure in place.

Bundled terms text can be displayed. Consent switches and submission stay disabled until `AuthDocuments.allowsConsentAndSubmit` is explicitly true. The login flag does not supply that confirmation.

## Selection and screen ownership

Selection uses stable diffable Study.ID, never a saved array index. Detail fetches independently. Back navigation retains the list and scroll position. Search owns a separate ViewModel/filter/snapshot and must not replace Main's list. No automatic refresh occurs on Detail return or search cancellation. UIKit/Combine observation and async Repository operations remain separate.

## MyPage

MyPage reads the existing SettingAccountViewModel's hidden/guest/checking/connectionFailure/member/logoutFailure states. It displays confirmed nickname only, keeps identity on logout failure, and provides explicit login/recheck/logout retry. SC52 owns authentication Tasks, cancellation and signup uncertainty; MyPage creates no session or network request. Profile and Settings share the same presentation/cleanup implementation. The profile's independent fullScreen stack never pops or replaces top-level tab stacks. Profile login completion/cancellation stays in the profile; gate login returns to the originating My Studies screen after the authentication sheet finishes safe dismissal.

## My Studies shared session

MemberAreaViewModel composes one account/list pair from a single RepositoryFactory graph. Checking hides private list data and selection; guest, hidden and connection failure become guest, unavailable and failure respectively. A confirmed nickname starts one member list request. Logout clears the list through the account publisher. The list asks the same account owner to recheck after authorization rejection or a retry while membership is unknown. An active logout/signup operation finishes before a queued recheck starts. A cancelled list result cannot restore old content. A refresh failure retains content; a successful empty response clears it. There is no pagination. The two tabs keep independent navigation stacks, and profile is fullScreen as described above.

A list authorization rejection permits one automatic account recheck. If that recheck still confirms the same member, the list stays in failure until explicit refresh; membership alone does not authorize an already rejected resource. A guest result preserves the onboarding instruction. Shared rechecks repeat failed pending-signup cleanup before restore, matching Settings recovery.
