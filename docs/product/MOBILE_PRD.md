# 모바일 앱 PRD — 결정된 방향과 남은 선택

상태: 사용자와 함께 구체화 중. 이 문서는 제품 의도를 기록하며 기능의 구현·배포 완료를 뜻하지 않는다.

## 제품 목적

디스코드에 익숙하지 않거나 UX 적응에 어려움을 느끼는 한국어권 사용자가 스터디를 쉽게 발견하고 이용할 수 있도록 진입 장벽을 낮춘다. 이는 리드가 제시한 제품의 출발점이며 사용자 전체에 대한 측정 결과를 뜻하지 않는다.

## 웹·앱과 디스코드의 역할

- 웹·앱은 서비스의 진입점이다. 스터디 탐색·검색·정보 확인·신청·관리를 가능한 한 웹이나 앱에서 처리하는 것이 목표다.
- 디스코드는 실제 스터디 활동이 이루어지는 장소로 둔다.
- 이 방향은 앱 내 채팅·음성 기능 구현을 승인한 것이 아니다. 디스코드 연결·입장 과정과 세부 관리 기능은 각각 범위를 정한다.
- 모든 웹 기능을 첫 앱 배포에 포함해야 한다는 의미는 아니다. 웹과 앱이 맡을 세부 기능은 서비스 흐름과 준비 상황에 맞춰 정한다.

## 결정된 앱 방향

| 항목 | 결정 |
|---|---|
| 중심 경험 | 스터디 탐색 |
| 초기 진입 | 비로그인 상태에서 스터디 목록으로 시작 |
| 기본 스터디 목록 | 모집 중인 스터디 기본 표시 (기본 탐색 목록의 노출 범위) |
| 하단 탭 | 스터디 / 내 스터디 2탭 |
| 비로그인 내 스터디 진입 | 내 스터디 화면에서 기능 안내와 로그인 버튼을 표시. 탭 선택만으로 로그인 화면을 자동으로 열지 않음 |
| 프로필·설정 진입 | 별도 프로필 버튼으로 진입. 설정이 늘어나면 독립 탭 분리를 재검토 |
| 탐색 방식 | 목록 둘러보기(모집 중 기본, `?status=OPEN`)와 검색(전체 공개 스터디 대상, 필터 기본값 전체, 모집 상태 + 카테고리 필터, 입력 멈춤 시 디바운스 자동 갱신). 기존 목록에서 UISearchController 결과 VC로 진입 및 기존 목록 유지 (상세 계획: [STUDY_LIST_SEARCH_PLAN.md](STUDY_LIST_SEARCH_PLAN.md)). status 파라미터는 코호트 모집 상태(DRAFT/OPEN/CLOSED)이며 스터디 레벨 상태와 구분한다 |
| 내 스터디·MyPage | 범위에 포함. 두 기능의 세부 경계는 논의 중 |
| 내 스터디 보기 방식 | 내 스터디 화면 안에서 참여 스터디 목록 / 캘린더 두 보기로 전환하는 내부 탭 구성 |
| My Calendar | 내가 참여한 스터디 일정 표시. 독립 하단 탭으로 두지 않고 내 스터디 내부에 배치 |
| 로컬 알림 | 참여 일정에 연결하는 기능. 세부 예약·권한·변경 정책은 논의 중 |
| 신청 | 장기 목표에는 포함하지만 현재 작업 범위에서는 제외. 후속 신청 스펙에서 별도로 구체화 |
| 현재 제공 범위 | 탐색·검색·상세·내 스터디/프로필 관리·참여 일정과 관련 기반을 구체화. 신청 관련 작업은 제외 |

현재는 신청서 작성·제출, 신청 진입 버튼, 신청 현황, 웹 신청으로 이어주는 임시 경로를 작업 범위에 넣지 않는다. 탐색·관리 기능의 완료를 신청 기능에 의존시키지 않는다. 웹 신청 연결은 허용 가능한 대안으로 남기되, 채택 여부·로그인 유지·신청 결과·앱 복귀는 후속 신청 스펙을 다룰 때 함께 정한다.

내 스터디의 리스트는 참여 스터디별 항목을 보여준다. 캘린더는 그 스터디들의 모임 일정을 모아 보여준다. 두 보기는 항목 단위가 다르며, 모임 일정 목록을 별도 보기로 추가하지 않는다. 내부 전환 컨트롤의 최종 디자인·표시 이름·기본 선택·선택 유지 정책은 아직 정하지 않았다.

하단 탐색 구조는 스터디 / 내 스터디 2탭으로 정했다. 프로필·설정은 별도 프로필 버튼에서 진입하며 버튼의 정확한 위치와 비로그인 시 동작은 후속 설계에서 정한다. 설정이 늘어나면 독립 탭이 필요한지 다시 검토한다. 현재 구현의 Main/Setting 구성이 이 결정대로 변경됐다는 의미는 아니다.

비로그인 상태에서도 내 스터디 탭에 진입할 수 있다. 이곳에서 참여 스터디와 일정을 확인할 수 있다는 안내와 로그인 버튼을 제공하고, 사용자가 버튼을 눌렀을 때 로그인 흐름을 시작한다. 이 안내는 로그인한 사용자에게 참여 스터디가 없는 빈 상태와 구분한다. 프로필 버튼의 비로그인 동작과 로그인 완료·취소·실패 이후 흐름까지 함께 확정한 것은 아니다.

초기 검색 진입(빈 검색어)은 검색창 플레이스홀더와 필터 영역만 표시하며, EmptyView 노출 및 전체 스터디 조회 요청을 발생시키지 않는다. 실제 검색어가 입력되어(디바운스 경과) 결과가 0건일 때만 '검색 결과 없음' EmptyView를 표시하며 로딩·실패 상태와 분리한다. 검색어를 모두 지우면 초기 플레이스홀더/필터 상태로 복귀하고 진행 중인 이전 요청 응답을 무효화한다.

## 필터와 BE 연동 확인

필터 범위는 모집 상태 + 카테고리로 제한한다. 요일·시간대 필터는 현재 범위에 넣지 않는다. 목록의 모집 상태 기본값은 모집 중이며, 검색 필터는 전체로 시작한다. 두 피처의 필터 상태는 독립적이다.

2026-09-18 확인한 BE develop(94d6eb3)은 category를 실제 조회 조건으로 적용한다. status는 최신 기수의 OPEN/CLOSED/DRAFT이며, DRAFT enum의 존재가 앱 노출 정책을 뜻하지 않는다. 현재 API는 기수가 없는 공개 스터디를 제외하므로 전체 공개 스터디 검색 정책과의 차이를 API 연동 시 확인한다. 실제 배포 API 호출은 검증하지 않았다.

## 기존 작업과의 연결

- 완료된 Mock 이슈는 완료로 유지하고 API 연결·디자인 개선은 후속 이슈로 연결한다.
- 각 이슈에는 관련 API·DTO 원본과 기준 버전, 디자인 시스템, 화면 캡처, 참고 구현을 연결한다.
- Feature Flag와 trunk-based 개발로 병행한다. 공통 정책·인터페이스를 맞추되 모든 화면을 순차 작업으로 묶지 않는다.
- 이슈는 에픽으로 사용하고, 구현은 기존 Notion 작업 DB에 등록해 이슈와 연결한다. 브랜치 `junsu/sc-{작업 ID}`와 커밋·PR 제목 `[sc-{작업 ID}]`는 실제 작업 ID를 기준으로 한다.
- 피처 플래그 생성 → 화면 구현 → API 작업 → 화면 API 연결 → Ready 전환을 출발점으로 삼는다. 화면은 View별로 나누고, 독립 기능 구현이 필요하면 별도 작업을 추가한다. 작업 본문은 할 일·완료 조건과 이슈 PRD 링크로 짧게 적는다. 공통 운영 문서에서 의존 관계를 관리하고 최종 1 PR 1 commit을 지향한다. 플래그 등록 후 API와 각 View는 병렬로 진행하고, 연결 작업은 양쪽 결과에 의존한다. 구체 규칙은 [작업 운영 원칙](../engineering/TASK_WORKFLOW.md)을 따른다.
- PRD는 ASD-STE100의 명료한 글쓰기 원칙을 한국어에 맞춰 약 80% 적용한다. 사용자 흐름·상태·의존 관계는 Mermaid, 비교는 표로 표현한다. 공식 표준 준수나 렌더 검증을 자동으로 뜻하지 않는다.

## 다음에 정할 내용

한 번에 하나씩 논의하고, 답변 전에는 추천을 결정으로 기록하지 않는다.

- 모집 상태·카테고리 필터의 선택 UI·레이블·배치, 검색 재진입 시 필터 유지 여부 (빈 검색어 진입 동작은 결정 완료: 플레이스홀더+필터 기본 표시, EmptyView 미표시, 전체 스터디 요청 미발생)
- 프로필 버튼과 검색 진입 위치
- 로그인 진입·취소·성공·온보딩·세션 만료 시 흐름
- 스터디 활동을 시작할 때 디스코드로 이어지는 방식

신청의 구체 흐름과 웹 연결 대안은 이번 논의 순서에서 제외하고 후속 신청 스펙으로 넘긴다.

디바운스 대기 시간은 구현 시 입력 반응과 요청 빈도를 확인해 조정한다. 사용자에게 별도로 선택받아야 하는 제품 결정으로 두지 않는다.
